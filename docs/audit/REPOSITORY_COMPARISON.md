# Repository Comparison — GitHub Skeleton vs. Replit Reference App

> **Historical record, dated 2026-07-28** — the reuse/refactor/reject decisions below
> drove the migration backlog (`docs/migration/REPLIT_TO_GITHUB_PLAN.md`) and remain a
> valid record of those decisions and their rationale. It does not describe the current
> codebase (most rows describe a "not implemented"/"greenfield" state that 16 merged PRs
> have since built out). For current-state architecture, see
> [`docs/architecture/current-state.md`](../architecture/current-state.md).

This matrix drives the migration backlog. For every capability, it states what exists in each repo and how the Replit version of it should be treated per your instructions: **Reuse**, **Refactor before reuse**, **Reimplement cleanly**, or **Reject**.

| Capability | GitHub (`jamalfrnk/LiquidAlpha`) | Replit (`LiquidAlphaBot`) | Classification | Why |
|---|---|---|---|---|
| **Wallet auth (nonce/signature/JWT)** | Not implemented — `auth.ts` is a broken email/password stub, disconnected from the schema and never mounted (GH F-1) | `auth-system.ts`: real EVM+Solana nonce/signature flow, crypto-random nonces, single-use, correct cookie flags, but no nonce TTL and no domain binding (Replit C-3, and audit "what's good") | **Refactor before reuse** (from Replit) | The core flow is sound and non-trivial to redo from scratch; needs a nonce-expiry column, SIWE-style domain binding, and a JWT-secret validation-at-boot fix before it's safe to depend on. |
| **Session/cookie handling** | Not implemented | Correct `httpOnly`/`secure`/`sameSite` flags in both live and dead auth files; 4 different hardcoded default secrets (Replit C-3) | **Refactor before reuse** | Cookie config pattern is right; secret-handling must be centralized and fail-closed. |
| **DB schema — users/markets/signals** | Minimal but internally consistent (`markets`, `signals`, `priceHistory`, `users`, `performance`), no FKs/indexes (GH F-10) | Much richer (`signals`, `configurations`, `activities`, `positions`, `users`, `sessions`), but 3 tables reuse a single generic `status` text column for unrelated lifecycles, and the migration history is out of sync with the live schema including a real column-name bug (Replit C-6) | **Refactor before reuse** | The richer entity set (positions, activities, configurations) reflects real product needs the GitHub skeleton hasn't reached yet — worth keeping the *shape* of these tables, not the generic-status pattern or the schema/migration drift. Rebuild as explicit state-machine enums and regenerate migrations from a clean baseline. |
| **Indicators (EMA/MACD/RSI/ATR)** | Working, correct Wilder-smoothed RSI, simple/clean implementations (GH inventory) | Same core math duplicated in `indicators.ts`; two signal engines exist, one dead with more advanced indicators (Fisher Transform/ADX/Keltner) but a flat-85 confidence bug (Replit H-3) | **Reuse** (GitHub's base) **+ selectively port** (Fisher/ADX/Keltner concepts from the dead Replit file, math only, not the confidence logic) | No need to reinvent EMA/MACD/RSI — GitHub's version is already clean. The advanced indicators are a genuine upgrade worth having, once decoupled from the flat-confidence bug. |
| **Signal confidence scoring** | Its own heuristic (`60` base + up to `+30`), same category of problem as Replit's (GH F-5) | Two heuristics: live one caps at 75 (additive, more honest), dead one hardcodes flat 85 regardless of match count (Replit H-3) | **Reimplement cleanly** | Neither is a calibrated probability. Rebuild as an explicitly-labeled "rule alignment score" with documented, versioned scoring logic — don't inherit either number scheme as-is. |
| **Signal evidence preservation** | Not implemented — `signals` table has no indicator snapshot, no stop/target (GH F-6) | `signals` table does store `target`/`stopLoss`/`price`, but not the indicator values or timeframe that produced them | **Reimplement cleanly** | Replit is closer (has stop/target columns) but still doesn't snapshot the deciding indicator values. Extend the schema properly rather than porting either as-is. |
| **Risk management (stop-loss/take-profit)** | `atr()` exists but is never called; no fields to store the result (GH F-11) | `signals.stopLoss`/`target` columns exist and are populated, but no server-side leverage/position-size caps or kill switch enforce anything at execution time (Replit H-2) | **Refactor before reuse** (schema) **+ reimplement** (enforcement) | Replit's schema fields are a head start; the actual risk *enforcement* (caps, kill switch) doesn't exist in either repo and is new work either way. |
| **Hyperliquid API client** | `hyperliquid-real.ts`: clean, Zod-validated, retry/backoff/timeout — best-quality file found in either repo, but the funding-rate endpoint shape is unverified against current Hyperliquid docs (GH audit "not yet evaluated") | Three parallel clients, only one (`hyperliquid-real.ts`) close to real, but its SDK is never actually instantiated (Replit H-1); order-placement routes have no auth | **Reuse** (GitHub's `hyperliquid-real.ts` as the starting point) **+ verify endpoint shapes against current API docs before relying on either** | GitHub's version is simpler and equally well-validated; don't import Replit's three-way duplication. |
| **Execution / paper trading** | Not implemented at all | Two live, materially different sim engines (`sim-adapter.ts` vs `simAdapter-new.ts`); one has a slippage model and limit-order fills, the other doesn't (Replit Duplication table); real trading path is stubbed/unauthenticated (Replit H-1, H-2) | **Refactor before reuse** (`simAdapter-new.ts`'s slippage/fill logic) **+ reimplement** (auth, risk gating, idempotency around it) | `simAdapter-new.ts`'s simulation fidelity is worth keeping; the missing auth/limits/idempotency around all execution endpoints is new work regardless of which sim engine is chosen. |
| **Market data ingestion** | CoinGecko polling every 10s, no WS, no fallback-data flagging | CoinGecko + Hyperliquid, but silently falls back to `Math.random()` fake prices on failure with no data-quality flag (Replit C-4); 5 different hardcoded fallback price sets across files | **Reimplement cleanly** | Both need a real "data quality / staleness" concept that neither has; don't port the silent-fake-data fallback pattern from Replit under any circumstances. |
| **WebSocket architecture** | Global broadcast, no subscriptions, no auth (GH F-4) — but at least the WS channel is the *only* data path, so it's not redundant with polling | Global broadcast (same problem) but *also* functionally decorative — real state comes from a dozen independent polling intervals while the WS pushes fabricated sim ticks that are only ever logged, never applied (Replit H-4) | **Reimplement cleanly** | Neither has a usable subscription model. | **REST API structure** | One clean registrar, `server.ts`, all routes in one place, but zero pagination/versioning/rate-limiting (GH audit generally) | Two competing registrars with silent shadowing (Replit C-1) — a structural bug, not just a style difference | **Reimplement cleanly**, informed by both | GitHub's single-registrar pattern is the right shape; its route *content* is thinner. Replit's route content (activities, positions, config, hyperliquid proxying) covers more product surface but must never be ported with two registrars again. |
| **Frontend (React client)** | Does not exist | 162 files: pages/components/hooks/lib, feature-based `features/trade`+`features/markets` pattern coexisting with an older, larger, unorganized `components/`+`hooks/` pattern; two `QueryClient` configs active simultaneously (Replit Duplication table); large (500-800 line) components mixing fetch+logic+render | **Refactor before reuse**, selectively, component by component — **not a bulk import** | This is explicitly called out in your instructions: do not copy the full client wholesale. The `features/trade`/`features/markets` hook pattern (`useAccount`, `useOrders`, `usePositions`, etc.) is the right shape and worth using as the *pattern* to extend; the older `hooks/`/flat `components/` pile, the 5 dead wallet-connect variants, and the dual QueryClient setup should not come along. |
| **Notifications (Discord/Telegram/email/push)** | Not implemented | `routes/notifications.ts` is entirely hardcoded in-memory mock data, no real delivery integration found | **Reject** (nothing real to port) | This is greenfield work in the target architecture regardless — there's no real implementation in either repo to reuse. |
| **Analytics / performance reporting** | `performance.ts`: honest, minimal PnL aggregation, no fake data | `routes.ts` returns `Math.random()`-generated "Sharpe ratio" and "max drawdown" as if real (Replit C-5) | **Reuse** (GitHub's honest minimalism as the starting shape) **+ reject** (Replit's fabricated-metrics pattern entirely) | GitHub does less, but what it does is truthful. Do not port any random-number performance metric under any circumstances — this directly violates your no-fabricated-claims guardrail. |
| **Dependency footprint** | Small, current, no dead deps found | 6 confirmed-unused Replit-OIDC-era packages (`passport`, `express-session`, etc.), 2 routing libraries mounted simultaneously, `hyperliquid` npm package installed but effectively unused | **Reject** (the unused deps) | Pure bloat, no functional value, drop entirely in the target repo. |
| **Testing** | None (no test script, no framework) | None (no test script, no framework) | **Reimplement cleanly** | Neither repo has anything to reuse here — this is greenfield in both cases. |
| **CI/CD** | None | None (Replit doesn't run CI at all in this export) | **Reimplement cleanly** | Greenfield — this is exactly what `chore/ci-foundation` (PR #2) is for. |

## Summary counts
- **Reuse largely as-is:** Indicator math base (EMA/MACD/RSI), `hyperliquid-real.ts` pattern, `performance.ts`'s honesty, GitHub's single-router shape.
- **Refactor before reuse:** Wallet auth flow, DB entity shapes (positions/activities/configurations), simulation engine (`simAdapter-new.ts`), frontend feature-hook pattern (`features/trade`, `features/markets`).
- **Reimplement cleanly (greenfield, informed by both):** Signal confidence/evidence model, market-data quality/staleness handling, WebSocket subscriptions, REST route structure, risk enforcement, testing, CI.
- **Reject outright:** Two-registrar route shadowing, silent fake-data fallbacks, fabricated performance metrics, dead wallet-connect/auth-hook/query-client duplicates, unused Replit-OIDC dependencies, generic `status` columns for distinct lifecycles.
